# Эксплуатация

## Текущее состояние

Интерфейс опубликован на GitHub Pages: `https://kugovv.github.io/so2-checker/`. Кнопка меню `@so2_check_bot` настроена на этот адрес. После отдельного разрешения владельца backend, PostgreSQL, очередь и бот развёрнуты на VPS. API: `https://so2-api.50.114.115.221.sslip.io`. Caddy выдал действующий сертификат Let's Encrypt, HTTPS проверен внешним клиентом. Интерфейс на VPS не размещён. Существующие `shadow-empire-admin` и `shadow-empire-bot` остались активны. Источник игровой статистики ещё не подключён; по UID `202777998` реальные матчи не получены.

Ниже — команды установленного backend. Сервисы и таймер резервного копирования включены в автозапуск. Проверены контролируемый перезапуск и восстановление дампа в отдельную временную БД; тестовая БД после проверки удалена. Образ приложения первоначально развёрнут из commit `083acb1b`, его идентификатор хранится в `/opt/so2-check/RELEASE`.

## Изоляция

Рабочий каталог `/opt/so2-check`, конфигурация `/etc/so2-check/app.env`, состояние `/var/lib/so2-check`, пользователь `so2check`, отдельная PostgreSQL БД/роль `so2check`. API слушает только `127.0.0.1:8171`; наружу выводится API через Caddy с HTTPS. `API_DOMAIN=so2-api.50.114.115.221.sslip.io` задан в `/etc/systemd/system/caddy.service.d/so2-check.conf`. В GitHub Repository variables `VITE_API_URL` указан тот же HTTPS origin. Интерфейс на VPS не обслуживается. Не изменять чужие сервисы, роли или proxy virtual hosts.

Секретный конфигурационный файл — `root:so2check`, режим `0640`, каталог `0750`. Игровая сессия хранится отдельным файлом `0600` и недоступна frontend. Роль PostgreSQL не суперпользователь, владеет только собственной БД. Резервное копирование ниже использует локальный Unix socket с peer-аутентификацией одноимённого пользователя. Существующие правила PostgreSQL других приложений не изменяются.

## Состояние, рестарт, журналы

```sh
systemctl status so2-check-api so2-check-worker so2-check-bot
curl --fail https://so2-api.50.114.115.221.sslip.io/healthz
curl --fail https://so2-api.50.114.115.221.sslip.io/api/status
systemctl restart so2-check-api so2-check-worker so2-check-bot
journalctl --namespace=so2-check -u so2-check-api -u so2-check-worker -u so2-check-bot -n 100 --no-pager
systemctl list-timers so2-check-backup.timer
```

`/healthz` проверяет БД отдельно от источника. `status=ok` не доказывает доступность Standoff: проверять `source_available` и успешный ответ профиля на реальном UID. Только один worker и один poller бота: удерживается PostgreSQL advisory lock на всё время процесса. Бот отказывается от polling при существующем webhook.

## Обновление

Frontend обновляется workflow Pages после push в `main`. Для backend: получить проверенный commit в отдельный каталог релиза, установить зависимости в отдельный venv, выполнить тесты, сделать резервную копию, остановить только сервисы этого приложения, выполнить `alembic upgrade head`, переключить каталог релиза и запустить сервисы. Проверить `/healthz`, `/api/status` и журнал. Изменение формулы требует `python -m app.recalculate` из `backend/` перед возвратом сервиса в работу, чтобы сохранённые матчи и графики использовали одну методику. Копию предыдущего релиза и дамп сохранять для отката; несовместимые миграции не откатывать поверх новых данных без отдельной проверки.

## Резервные копии

`infra/backup.sh` делает атомарный custom-format `pg_dump`, проверяет чтение `pg_restore --list` и только после успешной проверки переименовывает файл. Таймер — ежедневно около 03:20 UTC, копии хранятся 14 дней. Копии на том же диске не защищают от потери VPS; внешний backup destination владельцем не предоставлен, поэтому offsite-копирование ещё не настроено.

```sh
systemctl start so2-check-backup.service
ls -lh /var/lib/so2-check/backups
sudo -u so2check pg_restore --list /var/lib/so2-check/backups/FILE.dump
```

Восстановление сначала проверять в **новой отдельной БД**, не поверх рабочей:

```sh
sudo -u postgres createdb --owner=so2check so2check_restore
sudo -u so2check pg_restore --no-owner --no-acl --exit-on-error --dbname=so2check_restore /var/lib/so2-check/backups/FILE.dump
```

После проверки сменить `DATABASE_URL` на восстановленную БД и перезапустить только сервисы приложения. `--clean`, удаление рабочего тома или чужой БД автоматически не выполняются.

## Размер, хранение и лимиты

На первоначально осмотренном VPS: RAM 961 МБ, available около 388 МБ, диск свободен 6,2 ГБ. Эти ресурсы не подтверждают нагрузку 10 тысяч одновременно; требуется измерение реальной нагрузки после подключения источника. Выбран один процесс API и последовательный worker, без непрерывного опроса всех пользователей. Сохранённые профили возвращаются из БД, обновление ставится в очередь с TTL 300 секунд. Параллельные запросы одного профиля не создают повторных работ. Ограничения страниц и интервал источника задаются конфигурацией.

Фактический размер игровых записей пока измерить нельзя — реальных ответов нет. Полные диагностические ответы не сохраняются; хранятся только нормализованные компактные показатели, формула и результаты. Автоматического удаления матчей нет. После появления реальных данных измерить `pg_database_size` / `pg_total_relation_size`, рост за неделю и запас диска; политику архива менять явно, без молчаливой очистки. API выдаёт не более 10 тысяч последних архивных матчей с признаком усечения; это лимит ответа, а не удаление БД.

Namespace journald настроен через `/etc/systemd/journald@so2-check.conf` и ограничивает журналы приложения 40 МБ/7 днями. Файл access log Caddy ротируется по 5 МБ с тремя архивами. Журналы не должны содержать исходный `initData`, bearer, bot token, handshake или пароли.

## Матчи со скриншотов и личный рекорд

Команда `/match` в боте работает независимо от игрового источника. Pillow13 и системные пакеты `tesseract-ocr`, `tesseract-ocr-eng`, `tesseract-ocr-rus` установлены отдельно; обработка ограничена одним процессом OCR и одним ожидающим запросом. Бот имеет `MemoryHigh=192M`, `MemoryMax=256M`, `CPUQuota=60%`; распознавание завершается по тайм-ауту и очищает временные файлы, включая отменённые задания.

Миграция `0002` добавляет `screenshot_matches` и `personal_bests`. Перед обновлением: резервная копия, затем `alembic upgrade head` под пользователем `so2check` с закрытой конфигурацией приложения. Миграция не удаляет игровые таблицы. Все подтверждённые скриншоты хранятся без изображений; автоматической очистки записей нет. Ответ личного архива ограничен50 последними записями с `total/truncated`; более старые данные продолжают храниться и могут оставаться личным рекордом.

Рекорд берёт оба источника и использует для сравнения единый предварительный вариант K/D/A. У автоматически загруженных игр обычный рейтинг и сводка последних20 не меняются. Смена основного UID исключает рекорд предыдущего автоматического профиля; личные загрузки сохраняются. При смене версии формулы рекорд восстанавливается из исходных K/D/A.

Проверка приватности без авторизации: `/api/me/best` и `/api/me/screenshot-matches` возвращают401. Удалённый `/api/top` возвращает404. Для проверки OCR можно использовать приватный пример и команду из [screenshot-matches.md](screenshot-matches.md); оригинал изображения не публикуется и не включён в deployment-архив.

## Подключение игрового источника

Отдельный серверный TLS/RPC-клиент описан в [server-client.md](server-client.md).
Его диагностическая команда и unit не включают production-источник автоматически.

Требуется [проверка источника](source-capabilities.md) по действующему handshake. Не включать адаптер, пока не подтверждены точные ключи, разделение UID/internal ID, режимы, единицы дат, личные раунды и серверная пагинация. `SOURCE_ADAPTER` — Python factory `module:function`; пустое значение оставляет источник честно отключённым. При недействительной сессии показываются сохранённые данные и понятная ошибка, автоматического повторного входа в игровой аккаунт не предполагается.

## Telegram

После обновления рейтинга 16.11 применяется миграция **0003**: nullable-поле сохранённого ника в users. Напарники используют `so2-allies-v2-preliminary`; 5×5 — so2-comp-v2-preliminary с автоматическим использованием счёта, когда личные раунды неизвестны. Для согласованного пересчёта на сервере: `runuser -u so2check -- sh -c 'set -a; . /etc/so2-check/app.env; set +a; cd /opt/so2-check/backend; /opt/so2-check/venv/bin/python -m app.recalculate'`. Пересчёт выполняется одной транзакцией, обновляет участников, снимки и личные рекорды. Перед ним запускается `systemctl start so2-check-backup.service`. Старые снимки с корректным счётом пересчитываются автоматически; основание match_total_assumed_full явно отделено от настоящих личных раундов. Сохранённый ник меняется после подтверждения новой загрузки с ником в подписи; `/nickname` показывает подсказку.

`PUBLIC_URL` бота — опубликованный HTTPS-адрес Pages, а не URL репозитория `github.com`. Сервис `so2-check-bot` запущен; при старте aiogram устанавливает команду `/start` и кнопку меню. Inline-кнопка приходит в ответ на `/start`; обработчик и отсутствие конкурирующего polling проверены тестами. Проверка настоящего пользовательского входа внутри Telegram Android/iOS пока не выполнена. Главное Mini App-поле профиля бота при необходимости включается владельцем в BotFather: `/mybots` → нужный бот → Bot Settings → Configure Mini App → Enable Mini App, указать опубликованный URL. Это дополнение к уже настроенной кнопке меню, а не условие её работы.
