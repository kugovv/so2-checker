# Серверный клиент Standoff 2

Клиент находится в `backend/game_client/` и не требует запущенного Android,
эмулятора или компьютера владельца. Это отдельный инструмент чтения и проверки
протокола; получение реальной игровой сессии и подключение её к Mini App пока
не завершены.

## Подтверждённая граница

15.11.2026 проверен настоящий сервер `server.boltgaming.io:2223` с проверкой
сертификата и имени узла. TLS-only запрос `PlayerRemoteService.getPlayer2`,
код 23, получил RPC `401`: сервер требует входа. Именной запрос
`getPlayerByUid` без сессии получил `404`; работоспособность поиска UID этим
не подтверждается. Старый hello опубликованного Astandy получил `400`.
Пароли и выдуманные tickets в этих проверках не отправлялись.

Профиль `tls-rpc` следует изменениям закрытого
[PR #4 AstandyClient](https://github.com/BonePolk/AstandyClient/pull/4),
commit `6b0d97c0ed1d80fdd7b5f81000ecea1496366449`: дополнительный hello/AES
убран, TLS остаётся обязательным. Профиль `legacy-aes` оставлен только для
явной диагностики старого протокола. Автоматического переключения с передачей
одного ticket разным протоколам нет. Дескрипторы protobuf происходят из
опубликованного PyPI `0.3.0.2`, их происхождение и хеши записаны в manifest.
Наличие схем не доказывает совместимость всех игровых методов.

## Возможности клиента

- Проверяемый TLS, ограниченные размер кадра и распаковка LZ4, корреляция RPC,
  тайм-ауты, heartbeat и ограничение параллельности/частоты запросов.
- Вход с уже выданным игровым ticket из закрытого файла; ошибки входа не
  превращаются в успешную пустую статистику.
- Разрешение публичного UID с отдельным внутренним `gpid` и проверкой совпадения.
- Чтение страниц истории и подробностей матча по опубликованной схеме.
  Фактическая доступность этих методов требует авторизованной проверки.
- Управляемый предел сбора, в том числе 50 матчей, дедупликация и остановка
  при повторе страницы. Это предел попытки чтения, а не обещание глубины архива.
- Закрытый диагностический снимок и отчёт о присутствии полей. Неизвестные
  динамические свойства не превращаются в K/D/A или режимы по догадке.

Запросов покупки, торговой площадки, изменения профиля, приглашений и отправки
сообщений в клиенте нет. Сессии, пароли и auth-envelope в снимки не входят.

## Запуск

```sh
cd backend
python -m venv .game-venv
.game-venv/bin/pip install -r game_client/requirements.txt
.game-venv/bin/python -m game_client --preflight
```

На VPS установлен отдельный каталог `/opt/so2-check/game-client`, отдельный
venv `/opt/so2-check/game-client-venv` и команда:

```sh
sudo -u so2check /opt/so2-check/bin/game-client --preflight
systemctl start so2-check-game-probe.service
journalctl --namespace=so2-check -u so2-check-game-probe.service -n 30 --no-pager
```

`rpc_boundary_verified=true` вместе с `game_authenticated=false` означает
успешную диагностику отказа до входа. Это не рабочая статистика аккаунта.
Диагностический unit запускается по требованию, без постоянного опроса.
Общая блокировка `flock` предотвращает параллельные запуски CLI на VPS.
Команда ограничивает адресное пространство процесса 128 МиБ; диагностический
unit дополнительно ограничивает память 100 МиБ и время запуска 35 секундами.

После получения допустимого игрового ticket закрытый файл JSON содержит
поля `ticket` и необязательное `expires_at` — Unix-время окончания действия.
Файл должен принадлежать `so2check`, иметь режим `0600` и находиться в закрытом
каталоге. Не передавать ticket аргументом команды, не помещать в репозиторий.

```sh
sudo -u so2check /opt/so2-check/bin/game-client \
  --ticket-file /etc/so2-check/game-session.json \
  --uid 202777998 --max-matches 50 \
  --schema-report /var/lib/so2-check/source-captures/schema.json \
  --snapshot /var/lib/so2-check/source-captures/game.json
```

Снимки предназначены для ограниченной диагностики. CLI вызывается явно, а
не непрерывно; автоматического накопления файлов нет. Они не публикуются
через API или Pages и не являются нормализованной историей Mini App.

## Что ещё требуется

В просмотренных публичных клиентах нет законченного входа в Standoff 2 по
почте и паролю и проверенного продления игровой сессии. Google RPC принимает
игровой `authCode`, Bolt ID RPC принимает token; оба дополнительно описывают
`AppVerification` и `DeviceInfo`. Пароль Gmail не заменяет эти данные.
[Google описывает получение игрового auth code через Play Games SDK](https://developer.android.com/games/pgs/android/server-access).
Обычный OAuth-токен другого приложения или магазина нельзя считать игровым.

Для полностью автономной работы остаются два необходимых подтверждения:
допустимый способ первоначального входа отдельного игрового аккаунта и
поддерживаемое продление сессии. Одноразового ticket без механизма продления
недостаточно для обещания постоянной работы.

`SOURCE_ADAPTER` production остаётся пустым. После настоящего входа сначала
нужно проверить поля, время, режимы 5×5/2×2 и глубину истории. Затем установить
единственный collector с общей очередью и закрытым IPC: API и worker работают
разными процессами, поэтому нельзя просто создать по игровому соединению в
каждом. Неизвестный режим или ошибка декодирования должны оставаться ошибкой
источника, а не успешной пустой страницей.
