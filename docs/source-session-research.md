# Отдельный игровой аккаунт: проверка авторизации

Проверено 15.11.2026. В этом исследовании учётные данные не использовались, запросы авторизации в игровой сервер не отправлялись. Получение действующей игровой сессии и доступ к матчам ещё не подтверждены.

## Уточнённый вариант работы: сервер 24/7

Владелец выбрал работу независимо от включённого личного компьютера. Локальный эмулятор как постоянный сборщик исключён. Рассматриваются самостоятельный серверный клиент без интерфейса игры и, как запасной путь, отдельный удалённый Android с официальным клиентом.

Фактическая проверка с VPS: `server.boltgaming.io:2223` доступен по TLS1.3; сертификат проверен с CA опубликованного Astandy. RPC-запросы и учётные данные не отправлялись. Это **только транспорт**, не вход в игровой аккаунт, не подтверждение совместимости RPC и не получение статистики. Локальный транспортный preflight дал тот же результат.

На имеющемся VPS1ГБ `/dev/kvm` отсутствует; API/worker/бот и прежние приложения остаются активны. Android с игрой туда не устанавливался. Для отдельной Android-среды сначала требуется проверить запуск игры, Google Play Services, штатный вход, видимость профилей и историю; наличие headless-режима Android само по себе этого не подтверждает.

Запрос получить50 матчей сохранён как цель проверки глубины истории. Он не означает подтверждённый доступ к50 играм и не обходит ограничения самого игрового сервера. Уровень участников можно показывать лишь как отдельную метрику; он не заменяет MMR для оценки силы соперников.

## Что означает предоставленный email и пароль

У Standoff 2 нет подтверждённого собственного входа по такой паре. Официальная справка указывает внешние способы входа: Google, Facebook, VK, Game Center, Apple ID, Huawei ID. Фактический основной способ можно посмотреть в игре: **Настройки → Авторизация**. Адрес Gmail сам по себе не доказывает, что игровой аккаунт привязан именно к Google.

Источник: [справка Standoff 2, обновлена 13.08.2026](https://help.standoff2.com/ru/articles/5652586-привязать-способ-авторизации-к-аккаунту-standoff-2).

Обычный вход в Google через браузер подтверждает только доступ к аккаунту Google. Его нельзя объявлять действующей сессией Standoff 2 или заменять им игровой ticket.

## Подтверждённые поля Astandy

В установленном отдельно PyPI `astandy==0.3.0.2` дескрипторы protobuf содержат:

| Объект | Поля и назначение по схеме |
|---|---|
| `AuthGoogle` | `gameId`, `gameVersion`, `platform`, **`authCode`**, `locale`, `store`. Email и пароля нет |
| `GoogleAuthRequest` | `authGoogle`, `appVerification`, `deviceInfo` |
| `GoogleAuthResponse` | `ticket` либо `ticketBinary`, отдельно `playerTicket` |
| `GuestAuthRequest` | `authGuest`, `appVerification`, `deviceInfo`; у `AuthGuest` есть `token`, не email/password |
| `BoltIdAuthRequest` | `authBoltId`, `appVerification`, `deviceInfo`; у `AuthBoltId` есть `token`, не email/password |
| `Handshake` | `ticket` |

Сгенерированный метод `GoogleAuthRemoteService.encryptedAuth2` присутствует с кодом315. Наличие сгенерированного метода и полей не доказывает, что текущий сервер принимает такой запрос. Ни роль `BoltId`, ни смысл его `token` нельзя считать обычным Axlebolt email/password входом без документации и живой проверки.

`AppVerification` включает сведения о приложении, устройстве и проверке целостности. Эти поля не следует заполнять выдуманными значениями или считать способом обхода проверки клиента.

Сам `StandClient` принимает готовый `handshake`; при старте выполняет `hello`, затем `encryptedHandshake(ticket=...)`. Документированной функции обмена email/password на ticket или штатного экспорта ticket из официальной игры в исследованном пакете нет. README также указывает ограниченный срок сессии и инвалидирование при повторном входе в официальный клиент.

Первичный источник: [AstandyClient](https://github.com/BonePolk/AstandyClient), исследованные `client.py`, `services/handshake.py`, `generated/services.py`, `generated/protos/auth_message_pb2.py` опубликованного PyPI-пакета. Схема не является официальной документацией Axlebolt.

## Что требует Google Play Games

Штатная аутентификация Play Games выполняется Android SDK в контексте настроенной игры. Для серверного доступа SDK выдаёт **одноразовый server auth code**, запрошенный для OAuth client ID зарегистрированного игрового сервера. Сервер затем обменивает этот код на OAuth-токен. Проект и credentials настраиваются владельцем игры в Google Play Console.

Следствие: обычный web-login Google или OAuth-код другого приложения не подтверждает авторизацию для игрового сервера Standoff 2. Написать свой Google OAuth-клиент и автоматически получить вместо него credentials игры нельзя. Связь конкретного `AuthGoogle.authCode` с текущим штатным потоком игры требует проверки, она здесь не объявляется доказанной.

Источники: [Google: аутентификация Android-игры](https://developer.android.com/games/pgs/android/android-signin), [Google: server-side access](https://developer.android.com/games/pgs/android/server-access).

## Следующий практический шаг

1. На обычном официальном клиенте выяснить основной способ входа выделенного аккаунта и успешно войти этим способом. Для Google нужен Android с Google Play Services либо совместимая среда официального клиента. Если провайдер запросит 2FA, подтверждение должен пройти владелец штатным способом.
2. В самом клиенте проверить поиск заданного публичного UID, видимость чужой истории, наличие K/D/A, раундов, составов, MMR и фактическую глубину списка. Отдельный аккаунт не отменяет ограничения сервера и приватности: наличие параметра offset не доказывает доступ к50 или большему числу матчей.
3. Для прямого backend-клиента нужен поддерживаемый способ выдачи/обновления авторизованного игрового ticket либо предоставленный поставщиком серверный API. Если такого способа нет, самостоятельный вход в официальную игру ещё не означает готовую Python-интеграцию.
4. Независимый запасной путь — чтение разрешённой к просмотру истории из интерфейса официального клиента/пользовательского импорта. Он ограничен видимыми полями и не должен выдаваться за подтверждённый массовый API или полную историю аккаунта.

Пока не получены реальные ответы, источник приложения остаётся отключённым. Пароли, OAuth-коды и игровые tickets не включаются в эту документацию, frontend, репозиторий или журналы.

## Круглосуточный сбор без включённого личного ПК

**На существующем VPS такой игровой сборщик пока не подтверждён.** У VPS около1ГБ RAM и лишь несколько гигабайт свободного диска после размещения приложений; уже работающие чужие сервисы необходимо сохранить. Установка туда Android/игры не является обоснованным способом запуска. Самостоятельный клиент Astandy смог бы работать без запущенной игры при действующем ticket, однако поддерживаемое самостоятельное получение и продление ticket по email/password здесь не найдено. Следовательно, требование автономного24/7 входа пока не выполнено.

Технически headless Android существует: официальный Android Emulator поддерживает `-no-window` для серверов без дисплея и управление через ADB. Но отсутствие окна не устраняет потребность в CPU/GPU/памяти. Google рекомендует для полноценной среды16ГБ RAM/16ГБ диска; это рекомендация для комфортной работы, не гарантированный минимальный размер отдельного headless процесса. На Linux VM-ускорение использует KVM. Документация также ограничивает запуск ускоренного эмулятора внутри другой VM; обычный VPS без доступного аппаратного ускорения нельзя считать подходящим хостом. Нужна отдельная машина или явно совместимый облачный Android-узел.

Источники: [headless-флаг](https://developer.android.com/studio/run/emulator-commandline), [ускорение/KVM и ограничения](https://developer.android.com/studio/run/emulator-acceleration), [требования среды](https://developer.android.com/studio/run/emulator).

При этом Axlebolt прямо сообщает, что оптимизирует игру для мобильных устройств и **не поддерживает/не исправляет проблемы эмуляторов**. Поэтому даже более мощный сервер не доказывает совместимость Standoff 2 или успешный игровой вход.

Источник: [официальные ответы разработчиков](https://help.standoff2.com/en/articles/12974375-hottest-questions-from-the-standoff-2-community-everything-we-discussed-on-stream).

Конкретная серверная Android-платформа существует — **Genymotion PaaS**, с ARM64/x86_64 образами в AWS/GCP/Azure/Alibaba, удалённым дисплеем и ADB. В таблице поставщика для3D-игр указан класс `c6g.2xlarge`/`m5.2xlarge`, а лёгкие классы прямо обозначены непригодными для игр. Современные образы могут изначально быть unrooted. Однако Google Play Services не входят в них по умолчанию, и совместимость Standoff 2 не заявлена. Это только кандидат на отдельную проверку совместимости до какой-либо постоянной аренды; работающая интеграция не подтверждена. Подписок, покупок и аккаунтов в рамках исследования не создавалось.

Источники: [облачные образы и классы нагрузки](https://docs.genymotion.com/quickstart/paas_quickstart/), [состояния root по версиям](https://docs.genymotion.com/features/root/), [Google Play Services](https://docs.genymotion.com/features/opengapps/).

AWS Device Farm даёт настоящие удалённые Android-устройства, но remote access и test run ограничены150минутами. Этот режим является средой тестирования, а не готовым постоянным24/7 устройством для сборщика. [Лимиты AWS](https://docs.aws.amazon.com/devicefarm/latest/developerguide/limits.html).

Google Play Games on PC также не является решением для текущего Linux VPS: официально требует Windows10+,8ГБ RAM, SSD с10ГБ свободного места, GPU уровня UHD630,4 физических ядра и включённую виртуализацию. Эти требования сами по себе не подтверждают наличие Standoff 2 в поддерживаемом каталоге. [Требования Google](https://support.google.com/googleplay/answer/11358071?hl=en).

**BOLT ID пока не подтверждён как независимый вход в игровой протокол.** В официальном анонсе его текущая доступность ограничена сайтом и требуется первоначальная авторизация через привязанный Google/Apple ID. Наличие `AuthBoltId` в protobuf не означает, что веб-токен BOLT ID подходит к игровому RPC или даёт матчевую статистику. [Официальный анонс](https://t.me/play_standoff2/2217).

Практический вывод: личный ПК можно исключить из архитектуры, но для этого нужен либо подтверждённый прямой клиент с автономным обновлением игровой сессии, либо отдельный постоянно доступный Android-узел, на котором игра реально пройдёт штатный вход и покажет требуемые данные. Ни один из вариантов ещё не проверен на текущем аккаунте/игре. Рекомендовать покупку нового сервера как гарантированное решение пока оснований нет.
