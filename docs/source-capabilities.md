# Проверка источника Standoff 2

Проверено 15.11.2026, повторная проверка после получения игрового UID **202777998**. **Ответов с настоящими показателями игрока пока не получено.** Предоставлены UID, доступ к VPS, токен Telegram-бота и разрешение на размещение backend, но доступа к серверу игровых данных пока нет. Выполненные запросы к стороннему приложению и официальному магазину вернули отказы доступа, описанные ниже. Таблица полей описывает схему клиента, а не подтверждённые живыми ответами возможности. Производственный источник остаётся отключённым; статистика отсутствует.

Пакет PyPI `0.3.0.2` дополнительно установлен в изолированный локальный каталог: импорт `StandClient`, создание protobuf-запросов UID/истории и сборщик схемы probe проходят в Python 3.12.10. Сетевое подключение и актуальная совместимость с игрой не подтверждены.

## Что требуется для подключения

Для прямого Astandy-клиента нужен действующий handshake отдельного разрешённого игрового аккаунта; для интеграции с внешним поставщиком — предоставленный им API и сервисный доступ. SSH относится к VPS, токен Telegram — к нашему Telegram Bot API, UID 202777998 — к запрошенному публичному профилю. Они не предоставляют игровую авторизацию.

В README и документации Astandy нет воспроизводимой инструкции обычного входа или штатного экспорта handshake из официального клиента. Автор требует уже полученную сессию и описывает её ограничения. Поэтому пользователь без технического опыта не должен считать handshake обычной настройкой, которую достаточно найти в меню игры. В публичной истории канала автора отдельно упоминается его сервер получения специального токена; такой сервис не входит в опубликованный пакет и доступ к нему нам не предоставлен.

В клиенте соединение настроено на TLS `server.boltgaming.io:2223`; затем выполняются `hello` и `encryptedHandshake(Handshake(ticket=...))`. Библиотека использует встроенный сертификат CA. Не отключать проверку сертификатов. Handshake передавать через закрытый серверный файл; не через командную строку, stdout или frontend.

## Схема и ограничения

Во всех строках фактическая обязательность присутствия в живом ответе пока **не проверена**. Proto3 не гарантирует присутствия значения только потому, что поле объявлено; скалярный ноль, false и пустая строка могут отсутствовать на проводе. У динамического `Property.value` есть `oneof`, что позволяет отличить отсутствие значения от переданного нуля.

| Данные | Точное поле в опубликованной схеме | Тип / смысл | Область | Поведение при отсутствии |
|---|---|---|---|---|
| Публичный игровой ID | `Player.uid`, `MatchPlayer.uid` | string, отображаемый UID | профиль / участник матча | Не подставлять внутренний ID; профиль без корректного UID не закреплять |
| Внутренний ID | `Player.gpid`, `MatchPlayer.gpid` | string, внутренний идентификатор | профиль / участник | UID сначала разрешается отдельным запросом; без результата история не запрашивается |
| Ник | `Player.name`, `MatchPlayer.name` | string | профиль / участник | Показать UID, не придумывать ник |
| ID аватара | `Player.avatarId`, `MatchPlayer.avatarId` | string, идентификатор ресурса, не URL | профиль / участник | Локальная заглушка; не использовать ID как URL |

## Разрешение UID и проверка пагинации

Правильная последовательность: `PlayerRemoteService.getPlayerByUid(GetPlayerByUidRequest(uid=публичный_ID))` → `response.player.gpid` → `MatchesRemoteService.getPlayerMatches(GetPlayerMatchesRequest(gpid=внутренний_ID, offset=Offset(offset=0,length=20)))`. Сохранять публичный UID и внутренний gpid отдельно. Возвращённый `player.uid` должен совпадать с запрошенным.

`tools/probe_source.py` выполняет только чтение: авторизуется, разрешает UID, запрашивает offsets 0/20/40 по 20 матчей без неподтверждённых фильтров и составляет отчёт о схемах, наличии полей, именах/типах динамических свойств, количестве/пересечении страниц. Полные ответы, ники, ID участников и значения динамических свойств в отчёт не включаются. Из-за неизвестного ключа режима эти страницы ещё не являются последними 20 матчами выбранного режима.

```sh
python3 -m venv /opt/so2-checker/source-probe-venv
/opt/so2-checker/source-probe-venv/bin/pip install 'astandy==0.3.0.2'
chmod 600 /etc/so2-checker/game-handshake
/opt/so2-checker/source-probe-venv/bin/python tools/probe_source.py \
  --handshake-file /etc/so2-checker/game-handshake \
  --uid PUBLIC_NUMERIC_UID \
  --report-out /opt/so2-checker/source-probe-report.json
```

Без handshake CLI завершится с кодом 2 и объяснением, без подключения к игре. После появления handshake проверить фактический import, TLS, успешную авторизацию, разрешение нескольких UID и независимость режимов. Пустой RPC-envelope, который библиотека способна вернуть после таймаута, probe трактует как ошибку; пустая транспортная заглушка не считается ответом с нулём матчей.

Один пустой offset=20 не доказывает общий лимит 20: аккаунт может иметь меньше игр. Новые IDs в следующих страницах подтверждают более глубокую историю только для проверенного аккаунта в момент теста. Повтор страницы при изменении offset — отдельное ограничение источника. Требуются проверки нескольких активных аккаунтов и дат, а затем одинаковый фильтр завершённости/режима.

## Что нужно до включения производственного адаптера

1. Получить успешные живые ответы и обновить таблицу точными ключами, единицами, значениями режимов и обязательностью. Не использовать догадки вида `kills`, `mode`, `rounds` как доказанные имена.
2. Проверить приращения `reward.stats` против финальных K/D/A; сопоставить один матч с игровым экраном. Выделить личные сыгранные раунды, поздние подключения и выходы. При отсутствии обязательных показателей рейтинг остаётся отсутствующим.
3. По проверенным ключам написать строгий адаптер в нормализованный формат приложения; неизвестные режимы/статусы и некорректные записи исключать с компактной причиной. Исключить дуэли.
4. Сохранять формулу и исходные показатели, дедуплицировать по `matchId`, привязать участие через отдельные UID/gpid, хранить разрыв при непересечении окон. Ограничить timeout/retry, параллельность, частоту и страницы; соблюдать ограничения провайдера.
5. Секрет и клиент держать только на сервере. Отключить подробное логирование библиотеки; её импорт сам создаёт каталог журналов. Probe изолирует эти файлы во временном каталоге и удаляет после проверки. Не запускать непрерывный цикл с недействительной сессией.
6. Только после сверки реальных ответов подключить адаптер к worker и объявлять интеграцию проверенной. До этого endpoint статуса должен честно сообщать о неподключённом источнике.
